Phase 0 · Foundation · v0.1

Data Model Spec

复式记账内核的数据模型与架构决策。这份文档的核心论点只有一句:financial truth 必须落在 ACID 的关系型数据库,不能放 Firestore。配套 schema.sql 可直接执行。

01

关键架构决策:为什么不是纯 Firebase

你的默认 stack 是 React + Vite + TS + Tailwind + Firebase。前端、auth、实时协作继续用 Firebase——但总账(ledger)必须用 Postgres。

Debit · 痛点 会计要求强一致性事务、复杂多表 join(科目层级、期间汇总、跨实体合并)、以及「每张凭证借贷必须相等」这种硬不变式。Firestore 是文档型、最终一致、无原生 join、无事务级跨文档约束——这几样全是它的弱项。把 ledger 放 Firestore = 迟早对不上账。
Credit · 决策 Postgres 管 financial truth,Firebase 管体验层。你做 CV pipeline 时已经选了 Zeabur PostgreSQL + pgvector,基础设施现成,零额外成本。
PostgreSQL — Financial Truth
  • journal_entries / journal_lines
  • accounts(CoA)
  • invoices / einvoice_submissions
  • payments / allocations
  • audit_log(append-only)
  • 合并报表 / trial balance
Firebase — Experience Layer
  • Auth(firebase_uid 桥接)
  • 实时协作 / presence
  • UI 草稿 / 未提交状态
  • 通知 / push
  • 文件附件(Storage)

桥接点:app_users.firebase_uid。用户在 Firebase 登录,Postgres 用这个 uid 关联权限和操作。两层各司其职,不重叠。

02

ER 总览

核心是中间那条 double-entry 主轴:一切财务动作(开票、收付款)最终都过账成 journal_entries + journal_lines,余额永远从分录推导,绝不直接改。

organizations (multi-entity, parent_org_id 自引用做集团) │ ├─< memberships >─ app_users (RBAC + firebase_uid) │ ├─< accounts (CoA, parent_id 层级) │ ├─< fiscal_periods (open/closed/locked) │ │ │ └─< journal_entries ★ 凭证头 │ │ 不变式: Σdebit = Σcredit (trigger 强制) │ └─< journal_lines (account_id, debit, credit, base_amount) │ │ 过账回填 ↑ └─> accounts │ ├─< contacts (customer/supplier, tin 必填) │ └─< invoices ─< invoice_lines │ │ │ ├─> einvoice_submissions (MyInvois UUID/status) │ └─< payment_allocations >─ payments │ └─< audit_log (append-only, 全实体留痕)
03

核心实体说明

展开看每个实体的职责。完整字段见 schema.sql。

journal_entries + journal_lines P0★ 命门
复式记账的心脏。entries 是凭证头,lines 是借贷行。每行只能借或贷之一(CHECK NOT (debit>0 AND credit>0))。posted 时由 deferred constraint trigger 强制 Σdebit = Σcredit——这是整个系统不会算错账的根本保障。这块设计错了,后面全盘重来,所以放 Phase 0 第一优先。
accounts(Chart of Accounts)P0
科目表。account_type 五类(asset/liability/equity/income/expense),normal_balance 标借增还是贷增,parent_id 做层级。支持 MPERS/MFRS 标准模板,onboarding 时一键套用——直接修掉「会计师不熟」那条 con。
invoices + invoice_linesP0
销售/采购共用一张表,direction + doc_type 区分(含 credit_note / debit_note / self_billed)。发票 issue 后过账,生成 journal_entry 并回填 journal_entry_id。发票本身不动余额,余额永远走分录。
einvoice_submissions(MyInvois)P0
e-Invoice 原生内置的落点。记录每次向 LHDN 提交的 payload(55 字段 JSONB)、回传的 myinvois_uuid、status(valid/invalid/cancelled)、validation 结果、QR、数字签名。channel 区分 api 直连还是 peppol。这张表 = 你相对 Xero/QuickBooks 的核心差异化:它们靠插件,你原生。
payments + payment_allocationsP0
收付款与核销。一笔款可核销多张发票(allocations 多对多),收款同样过账成 journal_entry。
audit_logP0
append-only 留痕。应用角色只授 INSERT/SELECT,杜绝篡改,满足 PDPA 留存与审计要求。记录 before/after JSONB 快照。
exchange_rates / currenciesP1
多币种支撑。journal_lines.base_amount 始终存 base currency 折算值,合并报表跨实体汇总时直接用,不必每次重算汇率。Phase 1 启用,服务你的 JB–SG 跨境结构。
04

不变式 · 进 PRD 非功能性需求

Invariants

1. 余额只能由 posted journal_entries 推导,任何模块都不直接写余额。

2. Trial balance(Σdebit − Σcredit group by account)恒为零差。

3. 合并报表 = 跨 org 按 base_amount 汇总,沿 parent_org_id 聚合。

4. period 关账后拒绝该期间凭证增改(应用层 + status='locked')。

5. audit_log 不可篡改,只增不改不删。
